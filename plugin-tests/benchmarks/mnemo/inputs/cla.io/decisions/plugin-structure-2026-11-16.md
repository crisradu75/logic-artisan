# Decision 2026-11-16: mnemo plugin skills and structure

Topic: which skills `plugins/mnemo/` ships, and how the rest of the plugin is laid out (shared conventions, check scripts, hooks, templates, tests). Made with `/cla:shape-decision` on 2026-11-16. Builds on `cla.io/decisions/plugin-architecture-2026-11-16.md` (the "architecture decision"). It supersedes the architecture decision's `mnemo-setup-domain` name and, for secret-scan hits only, Q3's `inbox/` fallback.

Grounded in: this repo's `CLAUDE.md`, `.claude/rules/cla-economy.md`, `cla.io/project-facts.md`, `plugins/mnemo/skills/README.md`, the architecture decision; the CLA plugin's `hooks/hooks.json` and `hooks/probe-python.sh` (v2.3.0); and in `crisradu75/research`: `mnemo/build-guide/build-guide-report.md` and `cla.io/decisions/2026-11-15-mnemo-design.md`.

## Noted, not asked

- **Release:** settled by architecture decision Q10 (release tags) and the version-bump rule. (Since architecture Q14 the version is `VERSION` and the tag `v<semver>`; setup copies from a named tag, and each domain copy records it in `.claude/mnemo/stamp.json`.)
- **Outside service:** not applicable; the plugin calls no vendor.
- **Setup templates:** a file used by one skill lives in that skill's folder (e.g. `skills/mnemo-setup/templates/`); a file used by two or more lives at the plugin root. Follows from Q3 and the "shared files exist once" invariant. (Since architecture Q13 setup's templates live in `mnemo`'s `.claude/skills/mnemo-setup/templates/`, outside `mnemo-plugin/`, and they also hold the hook wiring (`settings-hooks.json.tmpl`) because the wiring is generated per domain; a file used by two or more copied skills lives under `mnemo-plugin/mnemo/`.)
- **Improve's rules:** the loop's rule location and PR flow belong to `mnemo-improve`'s own spec, still undecided (architecture decision Q8). That spec needs them first.
- **Reversibility:** a skill rename later costs one `mnemo-setup` re-run per domain (Q5) and a one-line scheduled-task prompt edit. (Since architecture Q12 that re-run is a refresh PR per domain.)
- **Commands / agents:** none. Skills already appear as `/mnemo:<skill>`; whether `mnemo-improve` uses subagents is for its spec. (Since architecture Q12 they appear as `/<skill>`, for example `/mnemo-capture`.)
- **Description length rule:** removing the "≤200 characters for chat" rule from `CLAUDE.md` is already an architecture-decision follow-up; the report's drafts are 168–177 characters anyway.
- **Unverified, to confirm in the spec step:** ~~`${CLAUDE_PLUGIN_ROOT}` is expanded in `SKILL.md` text~~ (dropped: replaced by architecture Q12, skills name domain paths); Windows hooks run through Git Bash; Python 3 is present in the cloud VM (must hold before the fail-closed commit hook ships); ~~where `claude plugin eval` expects its prompt file~~ (dropped: replaced by architecture Q14, the trigger tests run `claude -p` from `evals/`). Added by architecture Q12–Q13: repo-committed hooks run in a cloud session and block a bad commit (device test 2); skills in `.claude/skills/` load in cloud sessions (docs say yes; the device test only confirms); a cloud session with `mnemo` and a domain repo attached can write and push to the domain repo.

## Invariants

The architecture decision's invariants carry over, with these changes:

- Every skill except `mnemo-setup` stops when the repo has no `mnemo.schema.yml`. `mnemo-setup` stops on a non-empty repo without one unless the user confirms.
- `mnemo-setup` never overwrites a file in place; changes to `review-first` files go through a PR.
- A missing Python blocks commits, never a Stop. With no usable Python, nothing commits, the `inbox/` fallback included; Claude says so. The fail-open Stop hook stays loop-safe, as architecture Q7 requires.
- Every hook first checks for `mnemo.schema.yml` at the git top level, in POSIX shell, and exits 0 before probing for Python, so non-Mnemo repos are never blocked. (Since architecture Q12 the hooks load only in repos that carry the copy, so this early exit is a cheap safety net, no longer load-bearing. The stricter rule stays: with no Python, a commit command that changes folder towards a target outside a Mnemo repo is blocked.)
- The Stop hook backup commit (a clarification made after review) calls `mnemo_check.py save` (Q13), which runs every check on changed files, `secrets` included, before committing. If a check fails, it commits nothing and prints why. On success it pulls with rebase, commits and pushes right away (Q12), because a reclaimed VM loses unpushed commits. It exits 0 at once when `git status --porcelain` is empty.
- Hooks, `mnemo-review` and tests call checks only through `scripts/mnemo_check.py` (in a domain repo, its copy at `.claude/mnemo/scripts/mnemo_check.py`).
- Nothing under `tests/` or the evals folder ships in `plugins/mnemo/`. (Replaced by architecture Q14: nothing under `tests/` or `evals/` is in `mnemo-plugin/` or reaches a domain repo.)
- Added by architecture Q12–Q13: domain copies are generated and refreshed only by `mnemo-setup`, never hand-edited; each records its source tag in `.claude/mnemo/stamp.json`, and a copied file that differs from its stamped hash is drift that setup reports.

## Scaffold spec requirements (lessons from CLA)

- A live test in a real cloud session watches a commit that must be blocked get blocked; it is part of extended device test 2. A unittest that finds Python proves nothing (CLA `hooks/probe-python.sh` header, "NOTE FOR ANYONE TESTING THIS").
- A test pins the exit codes: the commit hook exits 2 with no Python, and the Stop hook exits 1 (a visible notice that blocks nothing) (CLA `test_probe_announces_failure_and_exits_non_zero`).
- `hooks.json` sets an explicit `timeout` sized to the worst-case `save` run, and a test ties the code constant to it. A killed hook enforces nothing (CLA `hooks/_dispatch_lib.py`, the 2 s git timeout bug). (Since architecture Q12 the timeouts sit in `.claude/skills/mnemo-setup/templates/settings-hooks.json.tmpl`, the wiring merged into each domain's `.claude/settings.json`; the tie test stays.)
- A test allows only the loader-recognised top-level keys in `hooks.json` (`$schema`, `description`, `hooks`, `modules`, `surface`) and, per matcher group, only `matcher` and `hooks`. The rationale goes in the script headers (CLA issue #254). (Re-targeted by architecture Q12: the settings loader is a different loader, so the plugin key set is dropped. The test now checks the settings hooks schema in `.claude/skills/mnemo-setup/templates/settings-hooks.json.tmpl`: only the `hooks` key at the top, known event names, per matcher group only `matcher` and `hooks`, and per hook only `type`, `command` and `timeout`.)
- A test checks that every `${CLAUDE_PLUGIN_ROOT}/...` path in `SKILL.md` and `hooks.json` exists in the packaged `plugins/mnemo/` tree (CLA #61, #264). (Replaced by architecture Q12–Q14: every domain path a copied skill or hook names maps through the copy map to a file in `mnemo-plugin/`.)
- Scripts resolve the repo from cwd with `git rev-parse --show-toplevel`, never from `__file__`, and a skipped check counts as a failure (CLA #52).
- `.gitattributes` sets `*.sh text eol=lf`; the caller checks with `-x`, not `-n`; tests use `sys.executable` (CLA #198, probe CRLF note).
- The `git commit` / `git push` matcher gets a cross-product unittest of command forms (`git -C x commit`, `-c k=v`, chained `&&`, newline continuations) (CLA lessons-learned 2026-08-29, PR #186).
- The `secrets` check is measured for false positives on redacted copies of real notes before the block is switched on (CLA lessons-learned 2026-08-29; cla-economy "real fixture first").
- A test checks that the `plugin.json` version equals the `marketplace.json` tag ref; a published tag is never moved, only the pointer (CLA CLAUDE.md release rules). (Replaced by architecture Q14: `VERSION` at a tag equals the tag, and a domain copy's stamp equals the tag it was copied from. A published tag is still never moved.)
- Each skill runs once for real on a scratch repo before its PR merges (CLA lessons-learned, `/cla:checkpoint` shipped unrun).
