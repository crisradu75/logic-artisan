# cleanup — Phase 4 final cleanup pass (full mechanics)

Phase 4's step-by-step procedure, run once after every change in the sequence is done. `SKILL.md`'s Phase 4 stub carries the load-bearing invariant (re-running the chain-level green gate, path-scoped staging); this file carries the recipe.

1. **Verify <base-branch> is green.** This repo's own workspace-wide build/lint/test commands (from `cla.io/project-facts.md`), plus its local-infra-dependent hard gate if any shipped change touched the tables/surfaces it covers.
2. **Plain-delete the merged leftover branches, then prune stale remote-tracking branches.** In this order — the prune is what makes the plain delete refuse:
   - **Find which leftover local branches merged, keyed off the branch itself:** for each change in the sequence, `gh pr view <branch> --json state,number,headRefOid` (`<branch>` per spec-to-pr's own resolution). A reused branch name can make that return an older PR, so also require `headRefOid` to equal `git rev-parse <branch>`: the PR this chain merged has the local branch's tip as its head. Only `MERGED` with a matching head qualifies. A branch whose PR is still open or closed unmerged, or whose head does not match (an older PR, or local commits never pushed), is left alone and kept out of step 3's report line; name a mismatched one in the report so the user can look.
   - **Remove each merged change's "Concurrent runs" worktree first.** If `/cla:spec-to-pr`'s own "Concurrent runs" worktree pattern was used for a change that merged, its branch is checked out there and `-d` would refuse it. Remove that worktree now (`git worktree remove .claude/worktrees/<change>`), then confirm the folder is gone, in this order:
     - Run `test ! -e .claude/worktrees/<change>`. On Windows, git can report success and leave the folder behind. A gitignored `node_modules` junction inside it is the usual cause.
     - If the folder survived, remove the link itself with `rm .claude/worktrees/<change>/node_modules`. This works in Git Bash and on POSIX. It deletes the link and leaves its target alone. In PowerShell, use `Remove-Item -Recurse .claude\worktrees\<change>\node_modules` without `-Force`. This form works in PowerShell 5.1 and 7. From PowerShell or cmd, `cmd /c rmdir .claude\worktrees\<change>\node_modules` also works.
     - Never `rm -r` or `rm -rf` the link in Git Bash. Through a junction, that can delete the target's files. In PowerShell, never combine `-Recurse` with `-Force`; the guard blocks that form. See `${CLAUDE_PLUGIN_ROOT}/hooks/block-unsafe-recursive-delete.py`.
     - Re-run `git worktree remove .claude/worktrees/<change>`. If git no longer lists it, run `git worktree prune`, then `rmdir .claude/worktrees/<change>` on the empty folder.
     - Re-run the `test ! -e` check. If the folder still exists, stop and report it.
   - **If this worktree's HEAD is on one of those merged branches, detach it first:** `git checkout --detach`. From a dedicated worktree, change-loop step 2's `git checkout -b <branch>` leaves HEAD on the last change's branch, and git refuses to delete a checked-out branch. Detaching keeps the same commit and working tree, and `ask-destructive-git.py` does not prompt on it. Skip it when HEAD is on `<base-branch>` or on a branch that did not merge.
   - **`git branch -d <branch>` on each merged branch.** Ship pushed with `-u`, so while `origin/<branch>` still exists locally, `-d` checks "merged" against that upstream: when the local tip is contained in it, git warns "not yet merged to HEAD" and deletes the branch with exit 0. The hook does not prompt on a plain `-d`. A refusal (`not fully merged`, or `used by worktree`) is expected when the tracking ref is already gone — the `git push origin --delete` fallback in `chain-merge.md` removes it too — or when the branch is still checked out in a worktree this chain did not remove. Record each refused branch for step 3's report line and move on; never retry with `-D`.
   - **Then prune:** `git fetch --prune`. `gh pr merge --delete-branch` deletes the branch on GitHub; the local `remotes/origin/feature/...` ref doesn't disappear on its own.
3. **Confirm no chain worktree is left; list the branches step 2 could not delete.** `git worktree list` should show nothing but `<base-branch>`'s checkout, the worktree this run itself is in, any worktree of a change that did not merge, and any worktree the user set up for reasons outside this chain — don't touch those. A merged change's worktree still listed means step 2's removal did not finish: go back and complete it. `git branch -a` should show nothing but `<base-branch>` **plus the branches step 2's `-d` refused**, and any unmerged branch it left alone on purpose. With `origin/<branch>` gone, a squash-merged branch is not an ancestor of anything on `<base-branch>`, so only `git branch -D` removes it — which `ask-destructive-git.py` prompts on. **This skill does not force-delete them.** Phase 4 is still part of the unattended run, and a prompt here waits for a human exactly as it would mid-chain; do not reach for `ALLOW_DESTRUCTIVE_GIT=1` either. Instead:
   - Put the refused merged branches in step 5's final report as one ready-to-run line, `git branch -D <b1> <b2> …`. The hook prompts once for the whole batch, while the user is present to answer it. If none is left (the chain ran from the primary clone, where `--delete-branch` removes the local copy, or step 2's `-d` took them all), say so instead.
   - A branch refused with `used by worktree` is checked out in a worktree step 2 did not remove (one the user owns, say). The report line is only runnable once that worktree is gone, so say which worktree holds it beside the line.
4. **Confirm every change in the original sequence is archived.** `ls openspec/changes/` should show only `archive/` (or only the changes that were deliberately left out of scope, if the run was explicit-mode over a subset).
5. Mark the "Final cleanup pass" task complete and report final status: which changes shipped, their PR numbers, the final `<base-branch>` commit, the `git branch -D …` line from step 3 (or that none is needed), and confirmation that the repo's full gate (build/lint/test + any local-infra hard gate) is all green.
