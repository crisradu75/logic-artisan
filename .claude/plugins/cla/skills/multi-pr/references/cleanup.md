# cleanup — Phase 4 final cleanup pass (full mechanics)

Phase 4's step-by-step procedure, run once after every change in the sequence is done. `SKILL.md`'s Phase 4 stub carries the load-bearing invariant (re-running the chain-level green gate, path-scoped staging); this file carries the recipe.

0. **Under the stacked policy — including a mixed run that fell back to it mid-chain — steps 1-3 change as follows.**
   - **Step 1's gate target.** Run the chain-level gate on each stack's LEAF branch (the deepest child of each lineage — a leaf contains its whole ancestry in order). A chain can be a forest — several stacks plus independents — so one leaf does not cover everything: gate every leaf, and each independent's branch. In a MIXED run, ALSO gate `<base-branch>`: merges landed there before the fallback, so it is not in its pre-run state. From a dedicated worktree, `git checkout <base-branch>` fails (the primary clone holds it — change-loop step 5's note); gate a detached checkout of the fetched ref instead (`git fetch origin <base-branch>`, then `git checkout --detach origin/<base-branch>`), and return to the leaf branch after.
   - **Step 2's prune.** Skip in a pure stacked run (no branch was deleted); keep in a mixed run.
   - **Step 3 does NOT apply to stack branches.** Every branch an open PR is based on MUST survive until the user lands the stack — deleting one orphans its child PRs. Remove only the branches/worktrees of changes that actually merged before the fallback.
   - **Step 4's archive confirmation runs per gated branch.** No single checkout shows every archive in a stacked forest — each leaf holds only its own lineage's. Run `ls openspec/changes/` on each gated branch; the UNION across leaves and independents must show the full sequence archived.
   - **The report's landing checklist** (step 5) is the ordered, parents-first command PAIRS per change-loop step 5-alt: retarget the child (`gh pr edit <child> --base <base-branch>`), then merge the parent (`gh pr merge <#> --merge --delete-branch`) — merge commits, never squash on a stack, and never delete a branch an open PR still bases on; the squash-required alternative lives in step 5-alt.

1. **Verify <base-branch> is green (merge policies only).** This repo's own workspace-wide build/lint/test commands (see `cla.io/project-facts.md`, falling back to `cla.io/overlays/multi-pr.md` if absent), plus its local-infra-dependent hard gate if any shipped change touched the tables/surfaces it covers. This is the one gate that's worth re-running at the CHAIN level even though every individual change already passed it standalone — a later change's merge can occasionally interact with an earlier one in ways neither change's own Test phase would catch alone.
2. **Prune stale remote-tracking branches:** `git fetch --prune`. `gh pr merge --delete-branch` deletes the branch on GitHub; the local `remotes/origin/feature/...` ref doesn't disappear on its own.
3. **Remove leftover worktrees; list leftover local branches for the user.** `git worktree list` should show nothing but `<base-branch>`'s checkout (and any worktree the user set up for reasons outside this chain — don't touch those). `git branch -a` should show nothing but `<base-branch>` **plus the expected leftovers**: the local copies of squash-merged feature branches. A chain run from a dedicated worktree leaves one per merged change, because `--delete-branch`'s local half fails there (change-loop step 5), and after a squash merge only `git branch -D` removes them — which `ask-destructive-git.py` prompts on. **This skill does not delete them.** Phase 4 is still part of the unattended run, and a prompt here waits for a human exactly as it would mid-chain; do not reach for `ALLOW_DESTRUCTIVE_GIT=1` either. Instead:
   - For each leftover local branch that belongs to this chain, confirm its PR merged: `gh pr view <pr> --json state` shows `MERGED`. A branch whose PR is not `MERGED` (still open, closed unmerged, or a stack branch per step 0) stays out of the list.
   - Put the confirmed ones in step 5's final report as one ready-to-run line, `git branch -D <b1> <b2> …`. The hook prompts once for the whole batch, while the user is present to answer it. If no branch is left over (the chain ran from the primary clone, where `--delete-branch` removes the local copy), say so instead.
   - A branch still checked out in a worktree cannot be deleted, so remove that worktree first (below); the report line is only runnable once it is gone.

   If `/cla:spec-to-pr`'s own "Concurrent runs" worktree pattern was used for any change in this chain, remove that worktree now (`git worktree remove .claude/worktrees/<change>`); its local branch then joins the list above rather than being deleted here. Then confirm the folder is gone, in this order:
   - Run `test ! -e .claude/worktrees/<change>`. On Windows, git can report success and leave the folder behind. A gitignored `node_modules` junction inside it is the usual cause.
   - If the folder survived, remove the link itself with `rm .claude/worktrees/<change>/node_modules`. This works in Git Bash and on POSIX. It deletes the link and leaves its target alone. In PowerShell, use `Remove-Item -Recurse .claude\worktrees\<change>\node_modules` without `-Force`. This form works in PowerShell 5.1 and 7. From PowerShell or cmd, `cmd /c rmdir .claude\worktrees\<change>\node_modules` also works.
   - Never `rm -r` or `rm -rf` the link in Git Bash. Through a junction, that can delete the target's files. In PowerShell, never combine `-Recurse` with `-Force`; the guard blocks that form. See `${CLAUDE_PLUGIN_ROOT}/hooks/block-unsafe-recursive-delete.py`.
   - Re-run `git worktree remove .claude/worktrees/<change>`. If git no longer lists it, run `git worktree prune`, then `rmdir .claude/worktrees/<change>` on the empty folder.
   - Re-run the `test ! -e` check. If the folder still exists, stop and report it.
4. **Confirm every change in the original sequence is archived.** `ls openspec/changes/` should show only `archive/` (or only the changes that were deliberately left out of scope, if the run was explicit-mode over a subset).
5. Mark the "Final cleanup pass" task complete and report final status: which changes shipped, their PR numbers, the final `<base-branch>` commit, the `git branch -D …` line from step 3 (or that none is needed), and confirmation that the repo's full gate (build/lint/test + any local-infra hard gate) is all green.
