# cleanup — Phase 4 final cleanup pass (full mechanics)

Phase 4's step-by-step procedure, run once after every change in the sequence is done. `SKILL.md`'s Phase 4 stub carries the load-bearing invariant (re-running the chain-level green gate, path-scoped staging); this file carries the recipe.

0. **Under the stacked policy — including a mixed run that fell back to it mid-chain — steps 1-3 change as follows.**
   - **Step 1's gate target.** Run the chain-level gate on each stack's LEAF branch (the deepest child of each lineage — a leaf contains its whole ancestry in order). A chain can be a forest — several stacks plus independents — so one leaf does not cover everything: gate every leaf, and each independent's branch. In a MIXED run, ALSO gate `<base-branch>`: merges landed there before the fallback, so it is not in its pre-run state. From a dedicated worktree, `git checkout <base-branch>` fails (the primary clone holds it — change-loop step 5's note); gate a detached checkout of the fetched ref instead (`git fetch origin <base-branch>`, then `git checkout --detach origin/<base-branch>`), and return to the leaf branch after.
   - **Step 2's plain deletes and prune.** Skip in a pure stacked run (nothing merged, no branch was deleted); keep in a mixed run, for the changes that merged before the fallback.
   - **Steps 2-3 do NOT apply to stack branches.** Every branch an open PR is based on MUST survive until the user lands the stack — deleting one orphans its child PRs. Remove only the worktrees, and delete (step 2's plain `-d`) or list only the branches, of changes that actually merged before the fallback.
   - **Step 4's archive confirmation runs per gated branch.** No single checkout shows every archive in a stacked forest — each leaf holds only its own lineage's. Run `ls openspec/changes/` on each gated branch; the UNION across leaves and independents must show the full sequence archived.
   - **The report's landing checklist** (step 5) is the ordered, parents-first command PAIRS per change-loop step 5-alt: retarget the child (`gh pr edit <child> --base <base-branch>`), then merge the parent (`gh pr merge <#> --merge --delete-branch`) — merge commits, never squash on a stack, and never delete a branch an open PR still bases on; the squash-required alternative lives in step 5-alt.

1. **Verify <base-branch> is green (merge policies only).** This repo's own workspace-wide build/lint/test commands (from `cla.io/project-facts.md`), plus its local-infra-dependent hard gate if any shipped change touched the tables/surfaces it covers.
2. **Plain-delete the merged leftover branches, then prune stale remote-tracking branches.** In this order — the prune is what makes the plain delete refuse:
   - **Find which leftover local branches merged, keyed off the branch itself:** for each change in the sequence, `gh pr view <branch> --json state,number,headRefOid` (`<branch>` per spec-to-pr's own resolution). A reused branch name can make that return an older PR, so also require `headRefOid` to equal `git rev-parse <branch>`: the PR this chain merged has the local branch's tip as its head. Only `MERGED` with a matching head qualifies. A branch whose PR is still open, closed unmerged, or a stack branch (step 0), or whose head does not match (an older PR, or local commits never pushed), is left alone and kept out of step 3's report line; name a mismatched one in the report so the user can look.
   - **Remove each merged change's "Concurrent runs" worktree first.** If `/cla:spec-to-pr`'s own "Concurrent runs" worktree pattern was used for a change that merged, its branch is checked out there and `-d` would refuse it. Remove that worktree now (`git worktree remove .claude/worktrees/<change>`), then confirm the folder is gone, in this order:
     - Run `test ! -e .claude/worktrees/<change>`. On Windows, git can report success and leave the folder behind. A gitignored `node_modules` junction inside it is the usual cause.
     - If the folder survived, remove the link itself with `rm .claude/worktrees/<change>/node_modules`. This works in Git Bash and on POSIX. It deletes the link and leaves its target alone. In PowerShell, use `Remove-Item -Recurse .claude\worktrees\<change>\node_modules` without `-Force`. This form works in PowerShell 5.1 and 7. From PowerShell or cmd, `cmd /c rmdir .claude\worktrees\<change>\node_modules` also works.
     - Never `rm -r` or `rm -rf` the link in Git Bash. Through a junction, that can delete the target's files. In PowerShell, never combine `-Recurse` with `-Force`; the guard blocks that form. See `${CLAUDE_PLUGIN_ROOT}/hooks/block-unsafe-recursive-delete.py`.
     - Re-run `git worktree remove .claude/worktrees/<change>`. If git no longer lists it, run `git worktree prune`, then `rmdir .claude/worktrees/<change>` on the empty folder.
     - Re-run the `test ! -e` check. If the folder still exists, stop and report it.
   - **If this worktree's HEAD is on one of those merged branches, detach it first:** `git checkout --detach`. From a dedicated worktree, change-loop step 2's `git checkout -b <branch>` leaves HEAD on the last change's branch, and git refuses to delete a checked-out branch. Detaching keeps the same commit and working tree, and `ask-destructive-git.py` does not prompt on it. Skip it when HEAD is on `<base-branch>` or on a branch that did not merge (step 0 returns HEAD to a stack leaf, which stays).
   - **`git branch -d <branch>` on each merged branch.** Ship pushed with `-u`, so while `origin/<branch>` still exists locally, `-d` checks "merged" against that upstream: when the local tip is contained in it, git warns "not yet merged to HEAD" and deletes the branch with exit 0. The hook does not prompt on a plain `-d`. A refusal (`not fully merged`, or `used by worktree`) is expected when the tracking ref is already gone — change-loop step 5's `git push origin --delete` fallback removes it too — or when the branch is still checked out in a worktree this chain did not remove. Record each refused branch for step 3's report line and move on; never retry with `-D`.
   - **Then prune:** `git fetch --prune`. `gh pr merge --delete-branch` deletes the branch on GitHub; the local `remotes/origin/feature/...` ref doesn't disappear on its own.
3. **Confirm no chain worktree is left; list the branches step 2 could not delete.** `git worktree list` should show nothing but `<base-branch>`'s checkout, the worktree this run itself is in, any worktree of a change that did not merge (a stack branch per step 0), and any worktree the user set up for reasons outside this chain — don't touch those. A merged change's worktree still listed means step 2's removal did not finish: go back and complete it. `git branch -a` should show nothing but `<base-branch>` **plus the branches step 2's `-d` refused**, and any unmerged or stack branch it left alone on purpose. With `origin/<branch>` gone, a squash-merged branch is not an ancestor of anything on `<base-branch>`, so only `git branch -D` removes it — which `ask-destructive-git.py` prompts on. **This skill does not force-delete them.** Phase 4 is still part of the unattended run, and a prompt here waits for a human exactly as it would mid-chain; do not reach for `ALLOW_DESTRUCTIVE_GIT=1` either. Instead:
   - Put the refused merged branches in step 5's final report as one ready-to-run line, `git branch -D <b1> <b2> …`. The hook prompts once for the whole batch, while the user is present to answer it. If none is left (the chain ran from the primary clone, where `--delete-branch` removes the local copy, or step 2's `-d` took them all), say so instead.
   - A branch refused with `used by worktree` is checked out in a worktree step 2 did not remove (one the user owns, say). The report line is only runnable once that worktree is gone, so say which worktree holds it beside the line.
4. **Confirm every change in the original sequence is archived.** `ls openspec/changes/` should show only `archive/` (or only the changes that were deliberately left out of scope, if the run was explicit-mode over a subset).
5. Mark the "Final cleanup pass" task complete and report final status: which changes shipped, their PR numbers, the final `<base-branch>` commit, the `git branch -D …` line from step 3 (or that none is needed), and confirmation that the repo's full gate (build/lint/test + any local-infra hard gate) is all green.
