# cleanup — Phase 4 final cleanup pass (full mechanics)

Phase 4's step-by-step procedure, run once after every change in the sequence is done. `SKILL.md`'s Phase 4 stub carries the load-bearing invariant (re-running the chain-level green gate, path-scoped staging); this file carries the recipe.

1. **Verify master is green.** This repo's own workspace-wide build/lint/test commands (see `cla.io/project-facts.md`, falling back to `references/project-context.md` if absent), plus its local-infra-dependent hard gate if any shipped change touched the tables/surfaces it covers. This is the one gate that's worth re-running at the CHAIN level even though every individual change already passed it standalone — a later change's merge can occasionally interact with an earlier one in ways neither change's own Test phase would catch alone.
2. **Prune stale remote-tracking branches:** `git fetch --prune`. `gh pr merge --delete-branch` deletes the branch on GitHub; the local `remotes/origin/feature/...` ref doesn't disappear on its own.
3. **Remove leftover local branches/worktrees.** `git branch -a` and `git worktree list` should show nothing but `master` (and any worktree the user set up for reasons outside this chain — don't touch those). If `/cla:spec-to-pr`'s own "Concurrent runs" worktree pattern was used for any change in this chain, remove that worktree now (`git worktree remove .claude/worktrees/<change>`) — the branch is already gone via `--delete-branch`.
4. **Confirm every change in the original sequence is archived.** `ls openspec/changes/` should show only `archive/` (or only the changes that were deliberately left out of scope, if the run was explicit-mode over a subset).
5. **Append one chain-level record to `cla.io/retro/multi-pr-runs.jsonl`** (log-only — there is deliberately NO analyzer skill for this yet; see "What this skill deliberately does not do" in `SKILL.md`). `/cla:spec-to-pr`'s own per-CHANGE ledger can't see the facts a chain owns — whether the discovered order held, gate/escalation outcomes, post-merge follow-ups, inter-change breakage, per-change timing-by-complexity — so this captures them structurally (not just in the prose running-notes) for a future retro. **Assemble the record per the exact JSON schema + per-field intent in `references/run-log-schema.md`** and pipe it to `scripts/log_chain_run.py` (a validating sibling of `/cla:spec-to-pr`'s `log_run.py`). Counts/flags + small arrays only, no prose. Pull the real figures from the per-run running-notes file, not a re-guess: `per_change[].approx_total_min` and `total_actual_min` are the measured timestamp deltas (Phase 3 steps 2/6), while `total_estimated_min` is Phase 1c's upfront prediction (recorded in Phase 1c step 4) — logging both is what lets a future chain calibrate its Phase 1c estimate against this one, so don't let either silently degrade back into a guessed number here. Best-effort: if the script exits non-zero (invalid JSON, oversize, or write failure — the stderr names which), note it and continue — a missing chain-log line never blocks the run (same non-fatal posture as `/cla:spec-to-pr`'s own run-log step).
6. **Commit the chain-log line to `master`.** Unlike `/cla:spec-to-pr`'s per-run line (which rides its feature PR), this record is written directly on `master` after the last merge, so it must be committed explicitly or it lingers as a dirty working tree that trips a later resume's clean-tree expectation. After a `git_state.py --expect-branch master` check, path-scope the add (never `-A`): `git add cla.io/retro/multi-pr-runs.jsonl` then `git commit -m "chore: multi-pr chain log"` and `git push`. (Skipped only when `CLAUDE_RETRO_DIR` points the ledger outside the repo — then there's nothing tracked to commit.)
7. Mark the "Final cleanup pass" task complete and report final status: which changes shipped, their PR numbers, the final `master` commit, and confirmation that the repo's full gate (build/lint/test + any local-infra hard gate) is all green.
