# Failure-mode checklist

A non-exhaustive list of things to look for when running `/cla:codify-learnings`.

This file is a **retro-time staging checklist** — it is read only by `codify-learnings`, not by normal work sessions. A lesson parked only here prevents nothing until it re-offends; route preventable lessons to a load-bearing artifact (memory / `CLAUDE.md` / `SKILL.md` / hook) instead (see SKILL.md "Lesson routing and escalation"). Keep this file under ~60 bullets (matching SKILL.md Step 2.6): when it grows past that, consolidate overlapping bullets and retire any whose lesson has graduated to *any* higher rung — memory, `CLAUDE.md`, `SKILL.md`, a hook, or a script.

This repo's own stack shape, verification-command set, and package-layout history are in `cla.io/overlays/codify-learnings.md` ("Repo stack + verification path") — read it alongside this checklist for the concrete commands/paths the bullets below refer to.

## Agent behavior

- [ ] Did Claude take >2 turns to identify the root cause of a bug? What signal was missed?
- [ ] Were there reverted edits, deleted files, or "actually, do it differently" corrections? What earlier check would have prevented them?
- [ ] Did the user have to repeat the same correction more than once?
- [ ] Did Claude propose an action that was rejected, then propose something similar again?
- [ ] Did Claude announce one plan and execute another?
- [ ] Were tool calls denied (permission prompts) for commands that should be in the allowlist?
- [ ] Did Claude ask the user a question whose answer was already in the conversation or files?
- [ ] Did Claude do work the user didn't ask for ("scope creep")?
- [ ] Did Claude commit to a classification, mapping, or default when the underlying data was genuinely ambiguous, without surfacing the choice to the user? (e.g. an entity that could map to more than one category, a key with no obvious match, a toggle whose intent is unclear) — these warrant a checkpoint, not a silent default.
- [ ] **Single-field patch in a structure where surrounding fields determine semantics.** When asked to "make X match Y" / "put X on the same side as Y", check whether other fields in the same structure (other entries in an ordered array, other entries in an i18n JSON, other keys in a config profile) define what X currently contrasts with. Changing one field can break an invariant (e.g. a running total no longer summing to its expected value, a key with no matching translation) or leave the structure inconsistent. Show the full structure and target end-state to the user before patching.
- [ ] **User question "why would X be relevant?" is often hypothesis-rejection evidence.** When the user pushes back on a proposed action with a question rather than a yes/no, treat it as a strong signal that the underlying model is wrong, not just as a request to explain. Stop, re-examine, and rebuild the model from scratch instead of defending the prior reasoning.
- [ ] **Fix the whole cluster of interdependent claims atomically.** When a doc or spec section has multiple interdependent statements (a formula, a variable's role label, a conditional), fixing one claim without auditing the rest leaves residual contradictions. Identify ALL passages that reference the concept and fix them together. See `cla.io/overlays/codify-learnings.md` for a real incident in this repo where one such fix missed a sibling copy.
- [ ] **Did a subagent's output trip a harness prompt-injection-neutralization notice?** Surface it to the user explicitly, even when judged benign, rather than silently self-adjudicating and continuing — a judgment call about suspected injected content belongs in the visible conversation, not only in Claude's own reasoning.

## Tooling and codebase

- [ ] Was a calculation's output silently wrong (returned a plausible-but-incorrect value rather than failing loudly)? A pure-math core is especially exposed here — an off-by-one in a sum or a mis-averaged blend looks plausible but breaks a conservation invariant.
- [ ] Was a sentinel value (`0`, `-1`, `""`) used to mean "not found" / "excluded" in a way that collided with legitimate data? (An intentionally-excluded entry getting a real sentinel value by design — make sure a genuine zero/empty value isn't confused with an excluded one.)
- [ ] Did a heuristic or lookup miss a real-world variant the user had to point out?
- [ ] Was a fallback path triggered by an unexpected value range rather than by a true failure?
- [ ] Was a tolerance / threshold too tight or too loose for the real distribution of inputs? This covers single-value tolerances too (a subprocess timeout, a retry count, a size cap), not just data thresholds.
- [ ] Were error paths swallowed (silent `catch`, no console error, no surfaced state)?
- [ ] Did the code or a script depend on a CLI tool, env var, or stdout-encoding default that differs between platforms — e.g. `cp1252` vs UTF-8 stdout, path-separator assumptions, a Git Bash builtin missing on some installs? Silent-on-affected-platform divergence is high-cost because it doesn't fail in dev — the bug surfaces only when someone runs on the other OS. **Cross-OS breakage is bidirectional** — audit *both* directions: when a repo was recently developed on one OS only, or when you hit one OS-specific bug, proactively check for the *other* OS's breakage classes rather than fixing only the one you tripped over. See `cla.io/overlays/codify-learnings.md` for whether this repo has been developed across more than one OS.
- [ ] **POSIX env-var / path defaults in cross-platform code.** `process.env.TMPDIR || '/tmp'`, hardcoded `/`-separated paths, etc. read POSIX-only assumptions and break on Windows where the var is unset. Use platform-neutral helpers (`os.tmpdir()`, `path.join`). This is invisible in dev when the dev box happens to have the var set.
- [ ] **`import.meta.url` → filesystem path MUST use `fileURLToPath`, never `.pathname`.** `new URL(...).pathname` leaves URL-reserved chars percent-encoded — notably `%20` for a space — so on a checkout whose path contains a space, an `execSync` `cwd` or `fs` call built from `.pathname` fails with ENOENT. Also strips the Windows drive-letter awkwardly. `fileURLToPath(new URL('..', import.meta.url))` decodes correctly on every OS. Grep `.pathname` when touching path-deriving code. See `cla.io/overlays/codify-learnings.md` for whether this repo's own checkout path has a space (the reason this bit for real here).
- [ ] **Node-version-default drift in tests.** Node defaults change between majors and can break tooling silently: Node 25+ enables the global Web Storage API (`localStorage`/`sessionStorage`) by default, which makes jsdom defer to Node's non-functional implementation and leaves `window.localStorage` `undefined` in every jsdom test. Fix in the app's own `vitest.config.ts` via `pool: 'forks'` + `execArgv: ['--no-experimental-webstorage']` (portable), not a `NODE_OPTIONS` shell prefix. Watch for this class whenever tests pass on one Node major and fail on another.
- [ ] **Bulk regex/find-replace on source needs an immediate typecheck.** When bulk-substituting across many call sites (e.g. renaming a field on a shared type, reshaping a return type), the substitution can silently produce syntactically or type-broken output. Run the workspace build/typecheck immediately after any bulk edit, BEFORE assuming success — the typechecker pinpoints the break far faster than discovering it in the running app.
- [ ] **Load-bearing keys, not display strings.** Some values are produced/consumed as *keys* (not display names) and passed back through a translation function. A change that swaps a key for a literal, or adds a new enumerated value without updating every place that enumerates the set (the domain-vocabulary source, the dataset, every locale file), breaks silently (missing translation, dropped entry). Watch for the same class in any smoke test that keys off literal UI strings. See `cla.io/overlays/codify-learnings.md` for this repo's own concrete file paths for this class of key.
- [ ] **`openspec status --json isComplete: true` is artifact-file presence, not task-box state.** A change with `proposal.md` + `tasks.md` + `specs/` files present but ZERO `- [x]` boxes ticked can still report complete. Before trusting "implementation done", verify with `grep -c '^- \[ \]' openspec/changes/<name>/tasks.md` — a non-zero unticked count means the status lied.
- [ ] **Peer-repo branch/working-tree mismatch when reading a file by path.** When reading a file from a peer/sibling repo, don't assume its checked-out working tree reflects the branch you expect — check `git status`/`git branch` first, and if the target file/dir is empty or missing, check `git log --all -- <path>` and `git show <branch>:<path>` before concluding the content doesn't exist.
- [ ] **A shared resource ceiling must be derived from its consumers, not chosen first.** When components share one timeout / memory / rate budget, sum their measured worst cases and size the ceiling to fit — don't pick a round number and then shrink the components into it. Shrinking is where the damage happens: a bound tightened to fit an arbitrary ceiling stops catching only the pathological case it was for and starts firing on ordinary load, which for a guard means failing open on exactly the busy machine it was protecting. Check the sum whenever a hook, handler, or worker pool grows a new call site — and note that a per-component test proves nothing about the aggregate.
- [ ] **skill-development plugin is for creating skills, not reviewing them.** `plugin-dev:skill-development` loads a large block of skill-creation guidance every time it's invoked — none of it useful for *reviewing* an existing skill. For audit / simplification / duplication-finding tasks, dispatch a code-reviewer `Agent` on the SKILL.md text or analyze the files Read directly. It's a creation tool, not a review tool.

## Workflow and process

- [ ] Did the user remind Claude of a project rule from `CLAUDE.md` that was already documented? (→ rule isn't load-bearing enough; consider a hook.)
- [ ] Did Claude run a destructive action without confirming?
- [ ] Did Claude make a compound shell command harder to read than necessary (`cd /x && cmd`, etc.)?
- [ ] Did a hook fire spuriously or fail to fire when it should have?
- [ ] Was a permission prompt repeated multiple times for the same tool? (→ candidate for the allowlist in `.claude/settings.json`.)
- [ ] **Was a change declared done without verification?** See `cla.io/overlays/codify-learnings.md` for this repo's exact verification path (build/lint/test commands + any smoke/e2e scripts). If a change under the app/package source shipped without at least that pass, that's the gap to close. **"Passed locally" ≠ "passes in a clean env":** a suite that reads env/config at import can pass on a dev box that has a local `.env` and fail in CI that doesn't — such tests must self-provide placeholder env (e.g. vitest `test.env`) to be hermetic.
- [ ] Did Claude commit, push, or merge without explicit user authorization? **KEPT after graduating the merge half to a hook** — `ask-destructive-git.py` now prompts on every `gh pr merge`, but this bullet is broader: commit and push remain uncovered, and the common failure is carrying an earlier "merge and clean" instruction forward onto later, unrelated work. Authorization is per-artifact, not a session-wide mode.
- [ ] Did a step take >2 minutes with no user-visible signal? (Note: any intentional demo-pacing delay in this repo's own code is by design — don't mistake it for a hang, and don't "optimize" it away; see `cla.io/overlays/codify-learnings.md`.) A genuine long silent gap is indistinguishable from "hung"; every real >2-minute step deserves at least one progress signal.
- [ ] **Main spec heading drift blocks `openspec archive` — pre-flight before invoking it.** All these surface only when the first delta-spec update arrives and the materialization step aborts:
  - **(a) Missing section headers.** `## Purpose` or `## Requirements` absent → "Requirement header appears outside the main `## Requirements` section". Detect: `grep -L '^## Requirements' openspec/specs/<capability>/spec.md` and the same for `^## Purpose`.
  - **(b) Legacy `### X` without `Requirement:` prefix.** Older specs use plain `### <Name>` headings; MODIFIED-block matching expects `### Requirement: <Name>` and aborts. Detect: `grep -n '^### ' <active spec> | grep -v '### Requirement: '`.
  - **(c) MODIFIED rename — delta uses the new heading, the active spec still has the old one.** Same abort signature as (b): the active spec heading must be renamed in the same archive commit. Detect: for each `### Requirement: <Name>` in the delta's MODIFIED block, confirm an exact-string `grep -F` hit in the active spec.
- [ ] **After `git push` resolves merge conflicts on a PR branch, GitHub recomputes `mergeable`/`mergeStateStatus` asynchronously (3–10s).** `gh pr merge` invoked immediately after the push can return `not mergeable` even when the conflicts are resolved. Poll `gh pr view <#> --json mergeable,mergeStateStatus` until `MERGEABLE`/`CLEAN` before retrying.
- [ ] **Two OpenSpec changes in flight that both modify the same capability spec → the second to merge hits a materialized-spec merge conflict.** Archiving materializes the delta into `openspec/specs/<cap>/spec.md` while a PR is still open, so a sibling change touching the same requirement produces a content conflict that needs a *semantic* merge, not a mechanical one. Expect it when two changes target the same capability; resolve by keeping each change's distinct requirements and union-merging shared ones.
- [ ] **Review/analysis agents given a paraphrase of an artifact instead of its verbatim text produce phantom findings.** When an `Agent` dispatch *describes* an artifact ("the component renders 6 rows", "[full text retained]") rather than inlining its exact bytes, the agent reviews the *description* and flags defects that exist only in the summary. Always paste the artifact verbatim, or have the agent Read the file.
- [ ] **Verify agent "Critical" findings against actual code before applying.** Agent dispatches can produce phantom findings even with verbatim source pasted in — the agent reads the bytes but builds the wrong mental model of control flow. When a finding asserts "code path X runs in context Y" / "step A happens before step B", verify against the actual code (one Read) before staging a fix. Cost of verification: <30 seconds; cost of applying a phantom fix: a misleading commit plus a revert.
- [ ] **Parallel-session branch contamination (worktrees).** `git status --porcelain` does NOT surface in-progress git operations (`cherry-pick`, `rebase`, `merge`, `revert`, `bisect`) on OTHER branches or worktrees; a parallel session mid-operation can switch the working tree under you between phases. See `cla.io/overlays/codify-learnings.md` for this repo's own worktree-directory convention. Before a commit boundary, verify you're on the expected branch and that `git add` scope is limited to the intended paths (prefer explicit paths over `git add -A`, which can sweep in another session's untracked files).

## Documentation drift

- [ ] Does `CLAUDE.md`, a `SKILL.md`, `README.md`, or a file under `docs/` describe a behavior that no longer matches the code? See `cla.io/overlays/codify-learnings.md` for this repo's own set of docs that must stay in lockstep with its core-logic source, and a real incident where one dropped term slipped through one of those copies.
- [ ] Is there a script/command/skill the user had to discover by grepping rather than by reading docs?
- [ ] Did the user explain something verbally that should be in `CLAUDE.md` or a `SKILL.md` instead?
- [ ] **Symmetric content across paired files tempts revert.** When asked to "document the relationship between X and Y" in both files (e.g. mirror sections in two SKILL.md files, mirror tables in two docs), pause before doubling the surface area. Ask whether a single-sided version (in the smaller / most-likely-read one, with a cross-reference from the other) would suffice — symmetric duplication is itself a maintenance liability.
- [ ] **Doc-table / stamp staleness on refactors.** When a refactor changes a concrete behavior described in a doc table (an entity list, a set of weights, a command list, script names), the surrounding prose often retains stamps from a prior change — nobody re-reads the prose during a refactor, only the code. Audit the affected table BEFORE merging.
- [ ] **`.claude/` skills + references drift after structural refactors.** A layout change silently rots `.claude/plugins/cla/skills/**/SKILL.md`, their `references/*.md`, and `.claude/commands/**`: they hardcode paths, commands, and symbol names that no build/test/lint ever exercises, so a stale skill mis-runs with zero error. After any layout/tooling change, grep `.claude/` for old paths/commands/symbols. See `cla.io/overlays/codify-learnings.md` for a real incident in this repo where this went undetected until caught by hand.

## Memory and persistence

- [ ] Did Claude save (or fail to save) a memory entry that the user later had to re-explain?
- [ ] Is there a piece of personal preference / project context that was load-bearing today and isn't in memory?
